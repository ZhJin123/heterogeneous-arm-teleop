# 案例：自研 6 轴主手 → 大族 Elfin3

> 这是一次真实部署的记录（脱敏、无厂商代码）。它验证了本 skill 的默认架构，也贡献了
> 几个"只有上真机才会暴露"的坑。

## 硬件

| 角色 | 设备 | 接口 |
|---|---|---|
| 主手 | 自研小六轴，支持零力拖动；J7 电机与夹爪已拆除，TCP = 裸法兰 | C++ 500Hz 零力环，30Hz UDP 144B |
| 从手 | 大族 Elfin3 + Jodell 夹爪，工具点 `tool230`（法兰轴向 230mm） | Flask + CPS SDK，MoveL 绝对目标，15Hz |

## 布局（实测）

- 世界系 = 从臂基座：X 前 / Y 左 / Z 上。
- 主手基座：世界 `(0.58, −0.88, −0.15) m`（前 58 / 右 88 / 下 15 cm），
  `R_WM = Rz(−90°)`（主手 +X → 世界 −Y、+Y → 世界 +X）。
- 两臂摆放相差 90°，**不是**并排同向。

## 架构

```
master_bridge (C++ 500Hz 零力) --UDP 30Hz--> bridge.py (15Hz 虚拟TCP)
    --HTTP--> robot_server.py (Flask + CPS) --MoveL--> Elfin3
```

- 主手 UDP：`q[7]`（rad，已乘电机方向）、`tcp_pos`（m，主手基座系）、`tcp_quat`（x,y,z,w）。
- 从手接口：`/teleop_start`（返回 PCS）、`/teleop_move`（绝对目标，返回 `ok`/`busy`）、
  `/teleop_stop`、`/health`（含 `tcp_active`）。
- 桥内：`math3d` / `virtual_tcp` / `mapper` / `motion_controller` / `guard`，与 scaffold 一致。

## 参数

| 参数 | 值 |
|---|---|
| rate | 15 Hz |
| k_pos / k_rot | 1.0 / 1.0 |
| vmax / wmax | 150 mm/s / 90 °/s |
| linear_acc | 300 mm/s² |
| radius | 10 mm |
| master deadband | 0.5 mm / 1.0° |
| min-step | 0.5 mm / 0.5° |
| 软限位 | 无（硬件急停为唯一安全边界） |

## 真实事故与修正

### 1) J6 符号：模型与实机反向

- 主手 FK 是从旧示教程序手抄的，J6 写成 `rotY(−q[6])`；URDF 的 joint6 轴是 `+Y`。
- 旧程序只用这条链算重力，而 J6 的重力矩恒为 0（末节质心在轴上、J7 质量置 0），
  所以符号错误多年未被发现。一上遥操作可视化就暴露：转 J6，模型反向。
- 修正：`chain.hpp` 与 `grav.hpp` 同步改成 `+Y`；TCP 位置不受影响（57.5mm 偏移沿 J6 轴），
  姿态与手腕映射恢复正确，零力手感不变（J6 重力矩仍为 0）。

**教训**：手写运动学链必须逐轴单动核对；只用于重力的链会掩盖零力矩轴的符号错误。

### 2) 基座布局符号

- 文档写的是 `(88, 58, −15)`（水平 88 / 前方 58），代码却按 XYZ 理解成 `X=+0.88, Y=+0.58`。
- 实际是 **前 58、右 88** → 世界 `(0.58, −0.88, −0.15)`。可视化里主手基座跑到错误象限。
- 修正：只保留一个 `layout_info()` 常量来源，面板与服务都从它取；`R_WM` 单独配置。

**教训**："水平/前方"这种口述坐标必须换成显式 XYZ；布局只留一处常量。

### 3) Elfin3 模型基座坐标

- 官方 `elfin3.urdf.xacro`：`world →(rpy 0 0 −90°)→ base_link →(rpy 0 0 +90°)→ elfin_base`，
  两段固定旋转抵消，控制器 Base = `elfin_base`。
- 若只取 `+90°`，整个模型绕 Z 多转 90°；用实机 `joint_deg` 反算 TCP 立刻能看出来
  （位置误差 ~0.67m、RPY 差 90°）。
- 修正：可视化 FK 的基座用**单位阵**，再用控制器真实关节角驱动；TCP 与 PCS 误差 0.0mm。

**教训**：URDF 的 `world` 链接可能带仿真摆位；先确认哪个 link 对应控制器 Base。

### 4) 主手网格包含已拆掉的 J7/夹爪

- `link6.STL` 沿 +Y 一直建模到 162mm，而裸法兰在 57.5mm；模型末端看起来还带着 J7/夹爪。
- 修正：可视化服务端在 `y=0.0575` 处裁剪（顶点压平面 + 去退化面），不加载 `link7.STL`。

**教训**：拆硬件后，CAD 网格不一定同步更新；用 TCP 偏移作为裁剪面。

### 5) 工具坐标系静默回退

- 从手 SDK 在"工具名不存在"时可能继续用默认法兰跑，坐标整体偏 230mm，表现为持续的
  求逆解失败（`Point Calculate fail`）。
- 修正：服务端启动时激活工具，失败则 **fail-fast 退出**；`/health` 暴露 `tcp_active`，
  桥发现未激活拒绝启动。

**教训**：工具激活必须可观测 + fail-fast，不能"告警后继续"。

## 结论

- 虚拟 TCP 增量映射在异构臂上工作良好：无需让两臂姿态一致，也不需要标定基座平移。
- 真正花时间的不是映射数学，而是**符号与坐标系核对**（J6、基座 90°、工具轴、URDF 基座）。
- 最小安全层 + 硬件急停足够；软限位、低速爬坡、工作空间预检在这个场景里没有带来收益。
